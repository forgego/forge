# Platform Security & Hardening

Forge provides CSRF, session, and security middleware. Enable and configure the components needed by your application.

---

## CSRF Protection & Exempt Paths

Forge integrates Gorilla CSRF middleware to defend state-changing HTTP requests (`POST`, `PUT`, `PATCH`, `DELETE`).

### How It Works
1. For HTML/SPA requests, Forge issues a cryptographically masked CSRF token using Gorilla CSRF.
2. Form submissions or AJAX calls must provide the token via the `X-CSRF-Token` header or `gorilla.csrf.Token` form field.

### Configuring CSRF Exempt Paths
Public webhook listeners (e.g. Stripe, PayPal, GitHub webhooks) and stateless REST APIs authenticated via bearer tokens must bypass CSRF verification. Configure exempt paths in `config/config.yaml`:

```yaml
security:
  csrf_secret_key: "set-a-persistent-secret"
  csrf_exempt_paths:
    - "/api/v1/*"
    - "/webhooks/stripe"
    - "/webhooks/logistics"
```

`NewServer` installs CSRF protection when `security.csrf_secret_key` is nonempty. It checks request paths against `security.csrf_exempt_paths`; there is no `csrf_enabled` setting.

## Secret Keys Configuration

For production, Forge requires three explicit, non-placeholder keys. Each must contain at least 32 bytes, and the values must be distinct. Supply strong, independent secrets through your secret manager.

```yaml
security:
  secret_key: "replace-with-a-unique-app-secret-of-32-plus-bytes"
  csrf_secret_key: "replace-with-a-unique-csrf-secret-of-32-plus-bytes"
  session_secret: "replace-with-a-unique-session-secret-of-32-plus-bytes"
```

:::warning Production Recommendation
If keys are omitted during development, Forge generates ephemeral random keys and prints a warning in the console. For production deployments, always provide fixed keys via environment variables or secrets managers (`FORGE_SECURITY_SECRET_KEY`, etc.) so that active user sessions survive server restarts.
:::

## Secure Session Cookies

All cookies generated by Forge adhere to strict security best practices:

- **`HttpOnly: true`**: JavaScript cannot access cookies, neutralizing Cross-Site Scripting (XSS) session theft.
- **`SameSite: Lax` / `Strict`**: Blocks cross-site request leakage.
- **`Secure: true`**: When `app.env` is `production`, cookies are only transmitted over TLS/HTTPS.

## Password Hashing: Bcrypt with Double-Hash Defense

Bcrypt has a well-known vulnerability: passwords longer than 72 bytes are silently truncated.

Forge mitigates this by passing incoming passwords through a SHA-256 pre-hash before feeding into Bcrypt (cost factor 12):
1. Any password (whether 8 characters or 500 characters) is hashed to a fixed 32-byte SHA-256 digest.
2. The digest is then processed by Bcrypt with a cryptographic salt.
3. This eliminates the 72-byte truncation boundary completely while preserving Bcrypt's resistance to GPU hardware attacks.

## CORS (Cross-Origin Resource Sharing)

`NewServer` does not read `server.cors` YAML settings. Register `server.CORS` on your router to configure permitted browser origins:

```go
srv.RegisterRoutes(func(r *server.Router) {
    r.Use(server.CORS(&server.CORSOptions{
        AllowedOrigins: []string{"https://store.example.com"},
        AllowedMethods: []string{"GET", "POST", "OPTIONS"},
        AllowedHeaders: []string{"Content-Type", "Authorization"},
    }))
})
```

## Security Headers

`NewServer` does not install `SecureHeaders` automatically. Register `server.SecureHeaders(nil)` on the router to add its default headers, including:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY` (or `SAMEORIGIN` for Admin embedding)
- `X-XSS-Protection: 1; mode=block`
- `Strict-Transport-Security: max-age=31536000; includeSubDomains` (when TLS is active)
